# Personal Gitea on WSL — setup, migration, and upkeep notes

Date set up: 2026-08-12. Environment: WSL2 Ubuntu, rootless Podman (aliased as `docker`).

## 1. What's running

- Image: `docker.io/gitea/gitea:latest-rootless` (rolling tag — Gitea has no tag literally called
  `stable`; `latest-rootless` is the closest equivalent, tracks newest release).
- Managed by a systemd **user** service via a Podman Quadlet unit (not a manual `podman run`).
- Web UI: `http://127.0.0.1:3000` — bound to localhost only.
- Git SSH: `ssh://git@localhost:2222/<owner>/<repo>.git` — bound to localhost only.
- Admin/only user: `akhil` (created via CLI, not the web installer — see §3).

## 2. Where everything lives

| What | Path |
|---|---|
| Quadlet unit (defines the container) | `~/.config/containers/systemd/gitea.container` |
| Gitea data root (repos, DB, avatars, etc.) | `~/onedrive/gitea-data/` → syncs to OneDrive |
| Bare repos specifically | `~/onedrive/gitea-data/git/repositories/akhil/*.git` |
| Gitea config (`app.ini`) | `~/onedrive/gitea-data/gitea-config/app.ini` |
| SQLite DB | `~/onedrive/gitea-data/data/gitea.db` |
| Your SSH key (reused, not new) | `~/.ssh/id_ed25519` / `.pub` |
| Old bare-repo folder (informal remotes, pre-Gitea) | `~/onedrive/warchives-git-remotes/` — still in use for repos not yet migrated |

`~/onedrive` is a symlink to your corporate OneDrive folder, mounted via WSL's 9p driver.
**Everything under `gitea-data/` therefore syncs to OneDrive automatically** — that's the whole
point of this layout.

## 3. Why it's configured the way it is (the non-obvious parts)

### `--userns=keep-id` — required, not optional
The 9p OneDrive mount force-owns every file as host UID/GID **1000** (that's your real user —
see `/etc/wsl.conf` automount options `uid=1000,gid=1000`). Rootless Podman normally maps a
container's internal UID 1000 to a **subuid range** (100000+) on the host, not to your real UID
1000. Without `keep-id`, Gitea's writes to the OneDrive-mounted volume would fail with permission
denied, because the 9p mount only lets UID 1000 write. `keep-id` makes container UID 1000 map
straight to host UID 1000, matching the file owner. **Do not remove this flag.**

### SSH port is 2222 inside the container too, not 22
This tripped up the first setup pass. The *rootless* Gitea image runs as a non-root user and
**cannot bind privileged port 22** — its built-in SSH server listens on container port **2222**
(set via `SSH_PORT` in `app.ini`, defaults to 2222 in the rootless image). The Quadlet unit
publishes `127.0.0.1:2222:2222` (host:container) — if you ever change this, map to container port
**2222**, not 22, or SSH will silently accept TCP connections and then reset them during the SSH
handshake (that's the exact failure mode I hit and fixed).

### `INSTALL_LOCK=true` — skips the web setup wizard
This env var makes Gitea auto-generate `app.ini` with defaults (SQLite DB, no external DB
container/password to manage) and skip the browser-based install wizard entirely. Trade-off: no
admin account exists yet after first boot — it has to be created via CLI (see §4). This is why
you never saw Gitea's install wizard page.

### `DISABLE_REGISTRATION=true`
No public signups — appropriate since only you use this instance.

### Bound to `127.0.0.1` only
`PublishPort=127.0.0.1:3000:3000` and `127.0.0.1:2222:2222` in the Quadlet unit. Nothing on your
LAN or Windows host's other interfaces can reach this Gitea instance — only processes on this WSL
box, via localhost.

### `AutoUpdate=registry` + `podman-auto-update.timer`
The Quadlet unit has `AutoUpdate=registry`, and `podman-auto-update.timer` is enabled
(`systemctl --user enable/start podman-auto-update.timer`) — runs roughly twice a day, checks the
registry for a newer `latest-rootless` digest, and if found, pulls it and restarts the container
automatically. No manual action needed to stay current. Check status any time with:
```
systemctl --user list-timers podman-auto-update.timer
journalctl --user -u podman-auto-update.service
```

### systemd user service + linger
The container is managed as `gitea.service`, auto-generated by Podman's systemd generator from
the Quadlet file — you never run `podman run` directly. `loginctl enable-linger akhil` was run
(no sudo needed) so your user's systemd instance — and this service — starts at boot without
needing an interactive login. Verify linger is still on with `loginctl show-user akhil`.

## 5. Repo migration — what happened, for the record

Moved 12 legacy bare repos from `~/onedrive/warchives-git-remotes/*.git` (plain filesystem-path
git remotes, no server) into Gitea, by: `git fsck --full` on source → `cp -a` into
`~/onedrive/gitea-data/git/repositories/akhil/<name>.git` → `fsck --full` on the copy → diff
`git show-ref` between source and copy → adopt via Gitea's admin API
(`POST /api/v1/admin/unadopted/akhil/<name>`, no re-clone, no rewrite) → verify commit hash via
API matches source → repoint local clones' `origin` (and, for 3 repos, a second `template` remote
pointing at `ai-knowledge-base.git`) to `ssh://git@localhost:2222/akhil/<name>.git`.

**9 repos kept, live in Gitea now:** ranger, kc-knv-integration-enablement, people-directory,
ai-knowledge-base, enterprise-ontology, henkel-ai-innovation, cpgr-ai-role,
merged-estate-pillar2-delivery, claude-codex-integration-playground.

**3 repos deleted outright (both from Gitea and from the old OneDrive bare-repo folder), per your
instruction:** richie, zellij-pane-switcher, cpg-ait-role. Their local working clones (e.g.
`~/warchives/richie`) were **not** touched — only the remotes were removed. `richie`'s local
clone still has 2 commits that were never pushed anywhere; they exist only in that local working
tree now. `zellij-pane-switcher`'s local `main` branch was already local-only before any of this
(never existed on the old remote either) — not something the migration caused.

**Old bare-repo folder status:** `~/onedrive/warchives-git-remotes/` still exists with the 9 repos
that weren't deleted, kept deliberately as a rollback cushion per your instruction ("keep until I
am sure"). It is safe to delete later, once you trust the Gitea copies — nothing currently reads
from it (all local clones were repointed to Gitea).

## 6. Day-to-day operation

```bash
# status / logs
systemctl --user status gitea.service
journalctl --user -u gitea.service -f

# restart (e.g. after editing the Quadlet unit)
systemctl --user daemon-reload
systemctl --user restart gitea.service

# stop / start
systemctl --user stop gitea.service
systemctl --user start gitea.service

# manual image update (auto-update normally handles this)
podman pull docker.io/gitea/gitea:latest-rootless
systemctl --user restart gitea.service
```

## 7. Backup and disaster recovery

Since everything Gitea needs lives under `~/onedrive/gitea-data/`, and that syncs to OneDrive,
**OneDrive's own history/versioning is your backup** for the data. To restore on a fresh machine:

1. Install Podman, confirm OneDrive sync has the `gitea-data/` folder locally.
2. Recreate `~/.config/containers/systemd/gitea.container` from §1 above (or copy it — it's a
   plain text file, worth keeping in a dotfiles repo).
3. `loginctl enable-linger akhil`
4. `systemctl --user daemon-reload && systemctl --user start gitea.service`
5. No need to recreate the admin user or re-adopt repos — they're already in the DB inside
   `gitea-data/data/gitea.db`, which came along with the OneDrive sync.

**Caveat:** if OneDrive sync is mid-flight (partial file sync) when Gitea starts, you could see a
corrupted SQLite DB or a truncated repo. If this instance's data ever looks wrong after a
sync-heavy period (new machine, after being offline a long time, etc.), stop the service, confirm
OneDrive shows "up to date" for `gitea-data/`, and only then start it.

## 8. Known limitations / things to revisit later

- No HTTPS. Fine for localhost-only access; would need real config if ever exposed beyond this
  machine.
- SQLite, not Postgres/MySQL — fine at this scale (personal use), would need migration if this
  ever needs concurrent multi-process access.
- The `migration` API token (§4) should be revoked — it's the one loose end from setup.
- `~/onedrive/warchives-git-remotes/` still holds 9 old bare repos as a safety net — revisit
  deleting it once you're confident in the Gitea copies.
