## Question

Firstmate already ships native Pi extensions (`.pi/extensions/fm-calm.ts`, `fm-primary-pi-watch.ts`, `fm-primary-turnend-guard.ts`, and `lib/fm-calm-*.ts`, `lib/fm-operational-input.ts`). What hook patterns, layout helpers, and operational-input handling do they use, and which can `pi-subagents` adapt directly instead of re-deriving from Firstmate's shell-script equivalents?

## Answer

`.pi/extensions/fm-primary-turnend-guard.ts` uses `pi.on("tool_call", ...)` to run two bash-blocking PreToolUse-style seatbelts (`runPretoolCheck`/`runCdCheck` calling `fm-arm-pretool-check.sh`/`fm-cd-pretool-check.sh`) and returns `{ block: true, reason }` to actually stop a `bash` tool call before it executes — proven against Pi 0.80.5 per the code comment. The same file's `pi.on("agent_settled", ...)` runs `fm-turnend-guard.sh`, and on exit code 2 sends a `followUp` user message via `pi.sendUserMessage()`, guarded by a `guardFollowupActive` module flag so the guard doesn't re-trigger itself on the settle it just caused. `fm-primary-pi-watch.ts` models one "session generation" object (`SessionGeneration`) bound in `pi.on("session_start")`/`"session_shutdown"` to own a supervised child process across Pi's five session_start reasons (startup/reload/new/resume/fork) without restarting Pi, and separately registers a live tool (`fm_watch_arm_pi`) whose `renderCall`/`renderResult` read a shared `WatchToolShellState` to draw a single merged call+result shell box. `fm-calm.ts` centralizes all transcript/tool presentation toggling behind `pi.on("session_start")`, `"agent_start"`, `"agent_settled"`, and `"session_shutdown"` hooks that call one `applyWorkingPresentation()` function, and it demonstrates safe, checked monkey-patching of Pi internals (`AssistantMessageComponent.prototype.updateContent` in `fm-calm-assistant-layout.ts`, `InteractiveMode.prototype.addMessageToChat` in `fm-calm-operational-user-layout.ts`) gated behind `installCalmPresentationAdapter()` try/catch so one broken adapter never takes down the extension. `fm-calm-visibility.ts` defines a `CalmTranscriptClass` union plus `calmPresentationHides(class)` as the single source of truth other files query instead of duplicating visibility logic, and `fm-operational-input.ts` shells out to `bin/fm-operational-input.sh` to encode/classify synthetic operational messages (kind-tagged, invisible-character-marked) so downstream code can tell "genuine user prompt" from "harness-injected nudge."

**Recommendation for `pi-subagents`**:
1. For the Primary Dispatch Guard, copy the exact pattern in `fm-primary-turnend-guard.ts`'s `pi.on("tool_call", ...)` handler: gate on `event.type === "tool_call" && event.toolName === "bash"`, extract `event.input.command`, run a synchronous/async check, and return `{ block: true, reason }` — this is the only confirmed-working example of a Pi tool_call hook actually vetoing execution (verified against Pi 0.80.5 per its comment); build the bash_bg/self-fork command-string matching directly into the extension's TS instead of shelling out to a bash script, since pi-subagents has no bash-script side to delegate to.
2. Reuse the `guardFollowupActive`-style re-entrancy flag and `deliverAs: "followUp"` call to `pi.sendUserMessage()` from `fm-primary-turnend-guard.ts`'s `agent_settled` handler for the Driver Turn-End Guard — it's the concrete solved pattern for "alert the primary without the alert being mistaken for genuine user input and without re-triggering itself."
3. Adopt `fm-calm-visibility.ts`'s pattern of one small typed enum (`CalmTranscriptClass`) plus one predicate function (`calmPresentationHides`) as the single arbiter of a presentation/visibility decision, and have every other extension file query that one function rather than re-deriving the condition — apply this to whatever "is this a subagent-status row/injected nudge" distinction pi-subagents needs across its own multiple hook files.
4. Reuse `fm-operational-input.ts`'s encode/classify approach (tag injected messages with a `kind`, mark them so later code — and the transcript layout — can tell "session_start fleet digest" or "blocked_permission alert" apart from a genuine user prompt) for the already-planned session_start fleet digest and agent_settled alerts, but implement the encode/classify logic natively in TS rather than shelling to `fm-operational-input.sh`, since that script is Firstmate-specific.
5. If pi-subagents ever needs a custom "fleet status" tool row (e.g., a `list_subagents` or `fleet_status` tool), reuse `fm-primary-pi-watch.ts`'s `WatchToolShellState`/`refreshWatchToolShell` box-shell pattern (one `Box` merging `renderCall` + `renderResult` into a single shell keyed by tool-call state) rather than inventing new render-slot plumbing — it's a small, self-contained, directly copyable pattern, unlike the calm-mode monkey-patches which are higher-risk and lower-value for pi-subagents' scope.

## Correction (2026-08-11)

Recommendation 1 above overstated firstmate's precedent. Re-checked `fm-primary-turnend-guard.ts`'s `pi.on("tool_call")` handler directly: it wires exactly two checks — `runCdCheck` (`fm-cd-pretool-check.sh`, directory-mutation guard) and `runPretoolCheck` (`fm-arm-pretool-check.sh`, protects firstmate's own `fm-watch` daemon commands). **Neither is the subagent-delegation guard.** That guard (`bin/fm-subagent-pretool-check.sh`, documented in `docs/subagent-guard.md`) is real and does deny delegation-shaped calls, but it classifies by the **tool's name** (stems like `agent`/`task`/`workflow`/`spawn` against `event.toolName`/`tool_name`) — a mechanism that only works for harnesses exposing distinct native delegation tools (Claude's `Task`, Codex's equivalent, Grok, OpenCode). Pi has no such tool: every Pi tool call the primary driver could misuse for self-fork is the flat `bash` tool, so a name-shape classifier can never fire regardless of what's inside the command. **Firstmate has no working precedent for content-classifying a Pi bash command as a self-fork/delegation attempt.** The `tool_call` veto *mechanism* itself (gate on `toolName === "bash"`, extract `event.input.command`, return `{block: true, reason}`) is still validated (proven against Pi 0.80.5 by the cd-guard and arm-guard) and worth reusing for pi-subagents' Primary Dispatch Guard — but the *classification logic* of what counts as self-fork needs to be designed fresh, not adopted from firstmate. See the pi-subagents implementation ticket for the Primary Dispatch Guard for the resolved classifier rule.
