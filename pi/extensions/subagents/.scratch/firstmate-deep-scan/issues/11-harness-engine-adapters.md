## Question

How does Firstmate's harness-adapters skill and per-engine supervision protocol docs (`docs/supervision-protocols/{pi,claude,codex,grok,opencode,unknown}.md`) define engine-specific busy/idle detection signatures and native CLI argument/prompt translation, and what does `pi-subagents` need to correctly adapt this for its four engines (`pi`, `claude`, `codex`, `agy`)?

## Answer

`.agents/skills/harness-adapters/SKILL.md` and `bin/fm-busy-lib.sh` define one semantic busy-state contract per engine, never a shared heuristic: claude uses lifecycle hooks (`UserPromptSubmit`/`Stop`/`StopFailure`/`SessionEnd`, source `claude-hook`) but explicitly cannot detect a manual interrupt (no hook fires, so state stays "busy"); pi/pi-signed use a project extension's `agent_start`/`agent_settled` + `ctx.isIdle()` (source `pi-ext`); grok is the sole exception with a rendered-tail regex match on the keybind footer (`Ctrl+c:cancel`), deliberately scoped only to `harness=grok` and never generalized; muse folds its own session-log JSONL for run start/terminal events (no hook exists); and codex has **no verified busy source at all** — `fm_busy_codex_appserver_observable` and `fm_busy_codex_hooks_verified` both `return 1` in `bin/fm-busy-lib.sh`, so codex always classifies `unknown codex-unverified`. `fm_busy_sources_for_harness()` in `fm-busy-lib.sh` returns an empty string for any harness not explicitly matched in its `case`, meaning an unrecognized engine trusts zero sources and any record for it is `source-mismatch` → `unknown`. `docs/supervision-protocols/unknown.md` is the fallback for any primary harness lacking a verified watcher adapter: drain wakes, pick "a supervision wait the harness can actually wake from," never invent a UI signature, use `fm-watch-arm.sh` only if a tracked background mechanism is proven to notify on exit, and explicitly instructs to "record new verification evidence before promoting an unknown harness to a named snippet" (i.e., `unknown` is a temporary, evidence-gated state, not a permanent one). Native flag translation is handled separately in the SKILL.md launch-profile-axes table (e.g. codex effort goes through `-c 'model_reasoning_effort="..."'` not a dedicated flag, grok caps effort at `high` and omits unsupported levels rather than failing), with the rule: "When a requested effort value is outside the harness-specific accepted set, `fm-spawn` records the requested `effort=` in meta but emits no effort flag for that harness."

**Recommendation for `pi-subagents`**:
1. Since `agy` has no Firstmate precedent, do not invent a busy/idle signature for it now. Model it exactly on Firstmate's codex treatment: gate agy's busy detection behind an explicit boolean-verification function (analogous to `fm_busy_codex_semantic_source`/`fm_busy_kimi_verified`) that starts `false`/unverified, so agy always classifies `unknown` (fail-closed, matching pi-subagents' already-decided `unknown` state) until someone empirically proves a concrete signal (hook, log file, or stable rendered token) against the real agy CLI.
2. Structure the busy-detection adapter interface in three source tiers, matching Firstmate's precedence: (a) semantic push sources (hooks/extension events — pi, claude), (b) semantic pull/fold sources (on-demand log parsing — muse-style, useful if agy exposes a session transcript file), (c) rendered-text regex fallback — reserve this tier for exactly one engine at a time and only after tiers (a)/(b) are proven absent, never as a default.
3. Apply Firstmate's asymmetric trust rule to any rendered-tail fallback used for agy or codex: a matched "busy" token can be trusted, but a rendered "idle"-looking screen should not be promoted to `idle` — keep it `unknown` unless a semantic source confirms settlement. This avoids false-idle results that would wrongly unblock a supervisor.
4. Do not assume claude/codex hooks "just work" in pi-subagents' environment the way the already-decided adapters imply — Firstmate's own codex hooks never fired for a firstmate-launched worker despite being wired identically to claude's. Pi-subagents should empirically verify hook delivery per engine in its actual Zellij-tab launch shape before trusting any hook-based busy/idle classification, and fall back to `unknown` (not `idle`) when unverified.
5. For the native CLI arg translator, adopt Firstmate's graceful-degradation rule for agy's `--effort` flag: if a requested effort level isn't in agy's accepted vocabulary (unverified today), record the requested value in the launch metadata but omit the flag from the actual launch command, rather than failing the spawn — this keeps launches succeeding while preserving the intended value for audit/debugging.
