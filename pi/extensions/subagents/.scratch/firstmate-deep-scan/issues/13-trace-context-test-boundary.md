## Question

How does Firstmate's trace-context library (`docs/trace-context.md`, `bin/fm-trace-context-lib.sh`) correlate logs/spans across a spawn chain, and what's the architectural boundary between its mocked unit tests and its `-live-e2e.test.sh` suite — which of these patterns should `pi-subagents`' test suite adopt for correlating subagent output and drawing its own mock/live boundary?

## Answer

Firstmate's trace-context library (`bin/fm-trace-context-lib.sh`, doc in `docs/trace-context.md`) mints a W3C `traceparent` per task, not per process: `fm_trace_context_resolve()` reuses a valid carrier already recorded as `traceparent=` in `state/<id>.meta` verbatim on relaunch, and only mints a fresh root (random ids from `/dev/urandom` via `od`/`tr`, flags `01`) when none exists; it never adopts the calling process's own ambient `TRACEPARENT`, so a persistent Secondmate routing many unrelated tasks always roots a fresh trace per task instead of merging them. The carrier is injected into the pane as `TRACEPARENT` through the same pre-launch channel as `GOTMPDIR` and recorded identically in the meta file, so injected and recorded values are provably the same string; enablement itself is resolved once per locked home session (`fm_trace_context_session_start`/`session_effective`, atomically published, bound to the session lock pid) and propagated to Secondmates as a frozen `FM_TRACE_CONTEXT=on|off` launch override, never as inherited trace identity. Every failure mode (entropy failure, delivery failure, metadata-append failure) omits the carrier and still lets the spawn proceed — `fm_trace_context_resolve` always returns 0. Testing is split cleanly: `tests/fm-trace-context-lib.test.sh` is pure-function unit coverage (source the lib, no backend, no spawn) while `tests/fm-trace-context-spawn.test.sh` drives the real `bin/fm-spawn.sh` twice against fake tmux + real git worktrees (`run_two_level`) to prove primary→secondmate→worker propagation and per-task rooting across a real nested spawn chain. Separately, the mocked/live boundary is per-backend: `fm-backend-zellij.test.sh` fakes the `zellij` binary entirely (canned numbered responses, no real binary needed, always runs) while `fm-backend-zellij-smoke.test.sh` talks to a real installed `zellij`, skips cleanly via `command -v zellij`/`jq` checks, forces an explicit non-default session name (`FM_ZELLIJ_SESSION="fm-backend-smoke-$$"`), and tears down only through `zellij_safe_delete` in `tests/zellij-test-safety.sh`, whose `zellij_refuse_if_unsafe` fails closed unless the name is non-empty, is *not* literally `firstmate` (the real default session), and is currently listed by `zellij list-sessions`. A further tier, `*-live-e2e.test.sh` (e.g. `fm-herdr-version-floor-live-e2e.test.sh`), adds an explicit opt-in env-var gate (`FM_HERDR_VERSION_FLOOR_LIVE_E2E=1`) on top of tool-presence skips, because it downloads real upstream binaries over the network — a strictly heavier bar than the always-run-if-installed smoke tier.

**Recommendation for `pi-subagents`**:
1. Give each spawned subagent a task-scoped correlation id minted fresh on first spawn and reused verbatim from the IPC/state file on relaunch/recovery, never adopted from a parent's ambient environment — so a driver → subagent → nested-subagent chain roots one id per task instead of merging routed work. Test the mint/validate/recover functions as pure unit tests with zero Zellij/engine involvement, mirroring `fm-trace-context-lib.test.sh`.
2. Add a second test file (mirroring `fm-trace-context-spawn.test.sh`) that drives the real spawn entrypoint against the mocked Zellij stub already decided in round 1, and asserts the correlation id recorded in the IPC state file is byte-identical to whatever gets injected into the pane before launch, with an explicit ordering check plus a two-level "spawn a subagent that itself spawns a nested subagent" case — this is the only way to prove cross-process correlation survives a real spawn chain, which static IPC fixtures alone can't prove.
3. Split test tiers exactly as Firstmate does: mocked-CLI tests run by default in CI (round 1's stub); a "smoke" tier runs against the real `zellij` binary whenever it's installed (`command -v zellij` skip, no extra gate) but only against an explicitly-named, non-default session; reserve a further opt-in-env-var `-live-e2e` tier only if pi-subagents ever needs to exercise a real third-party engine CLI or network resource end-to-end.
4. Port the fail-closed safety guard verbatim in spirit: before any test cleanup step kills/deletes a Zellij session or tab, require (a) a non-empty explicit name, (b) that name is not the tool's real default session name, (c) that name is currently listed as live — refuse on any ambiguity rather than proceed. Centralize this in one shared test-safety lib every smoke/live test sources.
5. Make correlation-id resolution fail-independent: an entropy/lookup failure should omit the id and let the spawn still succeed, never abort it — test this explicitly by stubbing the id source to fail and asserting the spawn still reports success with no id recorded.
