# Sandcastle patch snippets

Apply these snippets to the files generated by `sandcastle init`. They are concrete patterns, not a reason to overwrite project-specific changes. Locate the equivalent generated block and patch it in place.

## `.sandcastle/main.mts`

### Configuration

Add the resource limit near the iteration limit:

```ts
const MAX_ITERATIONS = 32;
// Maximum number of issue pipelines to run at once.
const MAX_CONCURRENT_ISSUES = 6;
```

### Shared Pi mounts

Add the host Pi mounts to the sandbox factory. Verify each host path first and remove unavailable optional extension paths rather than creating a fake mount:

```ts
const PI_SKILLS = [
  "code-review",
  "codebase-design",
  "diagnosing-bugs",
  "implement",
  "improve-codebase-architecture",
  "resolving-merge-conflicts",
  "tdd",
  "triage",
];

const PI_EXTENSIONS = [
  {
    hostPath: "~/.pi/agent/git/github.com/algal/pi-openai-server-compaction",
    sandboxPath:
      "/home/agent/.pi/agent/git/github.com/algal/pi-openai-server-compaction",
  },
];

const piSandbox = () =>
  podman({
    mounts: [
      {
        hostPath: "~/.pi/agent/auth.json",
        sandboxPath: "/home/agent/.pi/agent/auth.json",
        // Pi creates a sibling lock file during provider refresh.
        readonly: false,
      },
      {
        hostPath: "~/.pi/agent/models-store.json",
        sandboxPath: "/home/agent/.pi/agent/models-store.json",
        readonly: true,
      },
      ...PI_SKILLS.map((skill) => ({
        hostPath: `~/.agents/skills/${skill}`,
        sandboxPath: `/home/agent/.pi/agent/skills/${skill}`,
        readonly: true,
      })),
      ...PI_EXTENSIONS.map((extension) => ({
        ...extension,
        readonly: true,
      })),
    ],
  });
```

Do not mount the entire host Pi directory. The auth file is the only read-write mount. Never log it.

### Bounded issue execution

The generated code has one `Promise.allSettled(issues.map(...))` call. Keep the whole existing per-issue callback, but wrap it in this batch loop:

```ts
const settled = [];

for (
  let offset = 0;
  offset < issues.length;
  offset += MAX_CONCURRENT_ISSUES
) {
  const batch = issues.slice(offset, offset + MAX_CONCURRENT_ISSUES);
  const batchResults = await Promise.allSettled(
    batch.map(async (issue) => {
      // Existing createSandbox, implementer, reviewer, and sandbox.close logic.
    }),
  );
  settled.push(...batchResults);
}
```

The later rejection logging and completed-branch selection should continue to consume `settled`. This preserves `Promise.allSettled` failure isolation while bounding containers and agents.

### Optional approval provider

Only for a Pi-extension project that explicitly needs project-local approval:

```ts
import { pi as sandcastlePi, type AgentProvider } from "@ai-hero/sandcastle";

export function piApproved(model: string): AgentProvider {
  const baseProvider = sandcastlePi(model);

  return {
    ...baseProvider,
    buildPrintCommand(options) {
      const command = baseProvider.buildPrintCommand(options);
      return {
        ...command,
        command: command.command.replace(
          /^pi(?=\s|$)/,
          "bin/pi-approved",
        ),
      };
    },
    buildInteractiveArgs(options) {
      const args = baseProvider.buildInteractiveArgs?.(options) ?? [];
      return args[0] === "pi" ? ["bin/pi-approved", ...args.slice(1)] : args;
    },
  };
}
```

Ordinary Pi-agent projects should use `sandcastle.pi(model)` directly and should not add this file or wrapper.

## Prompt files

The four prompt files should each have a `# SKILLS` section that names only the skills relevant to that role and tells the agent to read `CONTEXT.md` and relevant ADRs when changing domain concepts.

### `plan-prompt.md`

```md
# SKILLS

The following skills are mounted at `~/.pi/agent/skills/`. Read the relevant
`SKILL.md` before acting and follow it where applicable:

- `triage` — issue intake, labels, and readiness.
- `codebase-design` — dependency and module-boundary reasoning.

Use only the skills relevant to this planning task. Do not invent issue or
triage facts that are not present in the issue data.
```

### `implement-prompt.md`

```md
# SKILLS

The following skills are mounted at `~/.pi/agent/skills/`. Read the relevant
`SKILL.md` before acting and follow it where applicable:

- `implement` — implementation workflow and delivery discipline.
- `tdd` — use for red-green-refactor when the task has a suitable test seam.
- `diagnosing-bugs` — use when the issue reports a bug, failure, or regression.
- `improve-codebase-architecture` — use for architectural or design work.
- `resolving-merge-conflicts` — use only if Git reports an active conflict.

Read `CONTEXT.md` and relevant ADRs before changing domain concepts or architecture.
```

### `review-prompt.md`

```md
# SKILLS

The following skills are mounted at `~/.pi/agent/skills/`. Read the relevant
`SKILL.md` before acting and follow it where applicable:

- `code-review` — review the branch against project standards and intent.
- `codebase-design` — assess module boundaries and design quality.
- `improve-codebase-architecture` — use for a real architectural improvement.
- `tdd` — assess whether changed behaviour has adequate tests.

Read `CONTEXT.md` and relevant ADRs before judging domain terminology.
```

### `merge-prompt.md`

```md
# SKILLS

The following skills are mounted at `~/.pi/agent/skills/`. Read the relevant
`SKILL.md` before acting and follow it where applicable:

- `resolving-merge-conflicts` — use when a merge conflict occurs.
- `tdd` — use when verification requires test changes or test diagnosis.

Read `CONTEXT.md` and relevant ADRs when resolving domain concepts.
```

Replace tracker-specific commands in the task sections using `issue-tracker-migration.md`. Do not leave `gh issue` commands in Gitea or GitLab prompts.

## `.sandcastle/CODING_STANDARDS.md`

Use this baseline unless the project already has stronger standards:

```md
# Coding Standards

## TypeScript and Pi APIs

- Use strict TypeScript. Avoid `any`, unsafe casts, and hidden global state.
- Preserve Pi extension contracts and use documented Pi APIs instead of private internals.
- Prefer explicit types at public boundaries and clear, narrow interfaces.

## Design and reliability

- Keep modules focused. Prefer explicit data flow and small composable functions.
- Handle async work, process/event listeners, and resources with clear cleanup.
- Surface actionable errors and preserve useful context for diagnosis.
- Never log credentials, auth material, or prompts that may contain secrets.
- Maintain backward compatibility unless the issue explicitly changes the contract.

## Testing and verification

- Test observable behaviour at the plugin boundary, including failure and cleanup paths.
- Use descriptive test names and deterministic test data.
- Run the formatter, `npm run typecheck`, and `npm run test` before committing.
```

Do not overwrite project-specific standards. Merge this baseline with them and keep the file concise.

## Pi-extension-only files

Only when the project is developing a Pi extension, add or preserve:

`.pi/settings.json`:

```json
{
  "packages": [".."]
}
```

A focused provider test should verify the optional approval wrapper. Ordinary Sandcastle projects do not need `.pi/settings.json`, `src/index.ts`, `src/sandcastle-agent.ts`, or `src/sandcastle-agent.test.ts` merely because they use Pi agents.
